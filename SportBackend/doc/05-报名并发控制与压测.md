# 报名并发控制与压测

## 已实现方案

Redis + Lua 做互斥准入，MySQL 悲观锁事务做最终规则校验与写入。Redis **不保存名额或积分副本**，不声称跨 Redis/MySQL 原子事务。

1. 按用户 ID、项目 ID 构造 Redis 锁键（统一 `{registration}` hash tag）。Lua 全部检查后一次申请，冲突时不留下部分锁。批量晋级一次申请所选用户及项目的锁。
2. 有限等待，默认 2 秒；获得锁后进入 `READ_COMMITTED` 数据库事务。所有入口按用户 ID 升序，再按项目 ID 执行 `SELECT ... FOR UPDATE`。
3. 获锁后重新查询参赛身份、重复记录、代表队人数、个人项目数、项目人数；小程序入口再次检查报名时间和赛次开放状态。
4. 同一事务内完成参赛身份创建、报名记录创建/恢复、晋级状态更新及下一赛次报名。批量晋级任何一条失败，整个批次回滚。
5. 数据库提交或回滚结束后，以 Lua 比较随机持有者 token 再释放 Redis 锁。释放失败仅记录日志，等待 TTL；不把已提交请求返回成失败。

锁租期默认 30 秒，数据库事务超时 15 秒。即使 Redis 锁提前过期，遵循同一数据库锁协议的报名写入仍由 MySQL 串行校验。数据库故障不需要补偿 Redis 名额，因为没有 Redis 名额计数。

Redis 不可达时拒绝写入并提示服务暂不可用，不静默绕过。锁争用超出等待时间提示“报名操作繁忙，请稍后重试”。这与“名额已满”等业务拒绝需要分别统计。

## 覆盖入口和规则

- 小程序 `/api/register/submit`，管理端 `/api/admin/registration/add`、`update`、`promoteTopN`、删除接口。
- 同一用户跨项目竞争由用户行锁保护；同一项目不同用户及不同代表队竞争由项目行锁保护。不同用户、不同项目可以并行。
- 个人限报按配置项目集合内 `status=0` 的不同项目统计。
- 代表队限额按配置项目中 `status IN (0,1)` 的不同参赛人统计；同一人晋级下一赛次不重复增加代表队人数。
- 项目上限沿用原口径：项目下所有赛次 `status=0` 的记录总数，不是每个赛次各自的名额。
- 已取消记录重新报名会复核限额并复用原记录；恢复报名会排除自身记录，避免将自身重复计入。
- 不允许取消状态直接晋级；重复设置相同状态为无操作。

本次不修改业务库结构，不执行业务数据回填。测试库直接使用 `sql/` 中现有建表脚本。

## 边界

- 这是“Redis 准入互斥 + 数据库锁下业务复核”，不是 Redis 缓存名额预扣、异步落库或两套名额校验。
- 同一项目写操作会串行化，目标是正确性与限制数据库争用，不保证提高峰值吞吐量。批量晋级会占用所选用户和项目锁。
- 报名规则、组别和代表队归属在压测期间应保持稳定。管理端修改这些配置不属于本次报名锁协议，也不会自动纠正历史超限数据。
- 直接 SQL 写入、其他绕过此 Service 的程序、已有重复/不一致记录，不在新增锁协议的保证范围内。
- 维持既有撤销晋级语义：删除紧邻下一赛次记录；不额外实现多级晋级链级联撤销。
- 现有 admin 路由认证不完善属于独立问题，不要把管理端直接暴露到公网压测。

## 本地启动

项目根目录执行（使用用户提供的 Windows Redis 目录）：

```powershell
& .\SportBackend\scripts\start-local-redis.ps1
```

脚本仅监听 `127.0.0.1:6379`，不载入原 Redis 目录里的 `dump.rdb`。运行文件在 `SportBackend/target/redis-local-6379/`，锁无需持久化。已有服务时直接复用，不结束原进程。

后端重新启动以加载改动：

```powershell
cd SportBackend
mvn spring-boot:run "-Dspring-boot.run.profiles=registration"
```

配置来自 `application-registration.yml`，不需要修改本地数据库/微信凭证。可用 `REDIS_HOST`、`REDIS_PORT`、`REDIS_PASSWORD` 覆盖连接配置。容器编排已增加内部 Redis 服务；本次没有运行 Docker 部署。

验证内容：

1. 两个独立 Service 实例、16 工作线程、32 次请求争抢 5 个名额，最终 5 条有效报名。

4. 同一队并发报名，代表队限额 2 人时仅两人成功。
5. 首次报名时并发重复提交，仅创建一个参赛身份和一条报名。

9. 批量晋级第二次插入失败，整个批次回滚。
10. Redis 锁争用不残留部分锁；旧持有者不能删除新持有者的锁。
11. 事务内重新检查已过期的报名窗口。

这些是正确性测试，不是 Apifox HTTP 压测，也不代表线上 QPS 或响应时间。未运行会向业务库写轮播图的 `BannerTest`。

## Apifox 验证准备

建议使用独立压测环境/专门赛事与测试账号。执行任何业务库写入前仍按项目约定确认。

接口：`POST http://localhost:8080/api/register/submit`

```json
{"sportsMeetingId": 1, "eventId": 1, "scheduleId": 1}
```

以上 ID 为格式示例，必须替换成自己的测试数据。每个模拟用户携带自己的 `Authorization: Bearer <token>`，不要用同一个 token 模拟所有用户抢名额。同 token 并发属于重复提交测试。

响应断言检查 JSON 的 `code`，不能只看 HTTP 200：当前小程序 Controller 对业务拒绝可能仍返回 HTTP 200 + `code=400`。

分别测试：不同用户抢最后名额、同用户重复请求、同用户跨项目限报、同队限额、取消后重报、晋级/恢复。记录成功、规则拒绝、锁等待超时、系统异常四类结果。

测试后用数据库核对最终记录数和重复记录，记录环境配置、并发用户数、总请求量、测试时长、吞吐量、P95、异常率。没有这些实测数据前，不在简历写“高并发吞吐提升 X%”。

## 可用于简历的技术表述

使用 Redis + Lua 原子申请用户与项目互斥锁，结合 MySQL `SELECT ... FOR UPDATE` 在事务内复核重复报名及多维限报规则；数据库事务结束后按持有者标识释放锁，并通过并发及故障注入测试验证报名限制和回滚行为。
