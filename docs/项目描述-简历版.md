## 完整版（7 条）

> **运动会管理系统**（全栈独立开发）2026.05–2026.07
> 面向学校运动会的一站式管理系统，覆盖报名、赛程、成绩、积分、破纪录审核全流程。微信小程序面向选手，Web 管理端面向老师/裁判，Spring Boot 统一提供 RESTful 接口，所有响应走 `Result<T>` 统一封装。

1. **架构设计**：独立完成三端架构与实现，设计 18 张数据库表，后端 100 个 Java 文件约 4300 行，小程序 76 个文件、管理端 30 个文件，2 个月完成 113 次迭代提交。

2. **报名系统**：实现组别级「每人限报 N 项」校验（`participant→team→group_type` 链路 + 状态过滤计数查询，正确处理取消重报边界）；报名按「项目×赛次」精确开放；支持一键晋级下一赛次并自动报名。

3. **成绩系统**：重构成绩按 `event_schedule`（项目×赛次）独立存储，解决预赛/决赛成绩相互覆盖问题；成绩按田赛/径赛区分单位（秒/米）展示、排序与换算。

4. **积分体系**：实现代表队总分批量刷新、加减分调整记录（可追溯）、跨组别总积分榜 Top3 金银铜徽章展示，总分编辑只读防手误。

5. **破纪录审核**：成绩达标自动标记为破纪录候选，管理端人工筛选审核、通过后事务性入册（`@Transactional`），保证成绩与记录状态一致。

6. **账号体系改造**：将微信静默登录重构为账号密码体系（BCrypt 加密 + JWT 7 天有效期）；编写一次性 Java 迁移脚本安全回填 30 条历史数据；支持 EasyExcel 批量导入参赛人员、重置密码；小程序新增登录页、改密码页、「我的参赛项目」页与游客模式。

7. **性能与并发（Redis + Lua，规划/实现中）**：报名接口用 Redis + Lua 脚本将「名额检查 → 限报校验 → 写入」在 Redis 端原子执行，解决并发报名下的超报/超限问题（Lua 脚本保证判断与扣减不被并发打断）；代表队总积分榜热点数据改用 Redis 缓存，加减分通过 Lua 原子更新缓存并异步落库，降低数据库聚合压力。

8. **工程质量**：遵循「spec 设计 → plan 实施 → 任务化提交 → 里程碑 review」流程；数据库结构变更同步维护 `sql/` 建表脚本，避免代码与表结构脱节；纯逻辑抽离编写 24 项单元测试；统一 `Result<T>` 响应封装与全局异常处理。

## 面试可能被追问的点（备好答案）

- **限报校验怎么做、取消重报怎么不漏算？**（带状态过滤的计数查询，只统计未取消的报名）
- **为什么成绩要按赛次独立存？**（预赛/决赛同项目，存项目上会互相覆盖；加 `event_schedule_id` 作最小记录单位）
- **数据迁移怎么保证安全？**（先备份 → 一次性 Java 脚本回填 → 校验关联完整 → 迁移完成后清理临时代码）
- **项目是多人还是单人？**（单人全栈独立开发；文档化流程用于自管理）
- **数据库改动怎么维护一致性？**（强制约定：DDL 变更后必须同步更新 `sql/` 建表脚本）
- **Redis + Lua 用在哪、为什么用 Lua？**（报名防并发超报：名额/限报「检查+扣减」必须原子，拆成两条 Redis 命令会有竞态；用 Lua 脚本在 Redis 内一次执行保证原子性。积分榜缓存：热点读缓存、写回时经 Lua 原子更新。备选答法：也可用来做令牌桶限流）
- **Redis 与数据库的一致性怎么保证？**（缓存先失效或双写 + 定时刷新兜底；积分以数据库为准，Redis 只是加速层）
