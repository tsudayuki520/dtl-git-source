# 小程序赛况页优化说明

## 架构与实际数据流

- 后端：Spring Boot → Controller → Service → MyBatis Mapper/XML → MySQL，接口使用 `Result<T>`。
- 管理端：Vue 3 + TypeScript + Element Plus，按运动会 → 轮次 → 项目录入成绩。田赛成绩保存为厘米，径赛和团队赛保存为毫秒，积分独立保存。
- 小程序：原生 WXML/WXSS/JS，底部“赛况”对应 `sportdocu/pages/match/`；`pages/result/` 是独立的团体总分排行页。
- 轮次由 `event_schedule` 关联项目与 `schedule`；成绩通过 `event_schedule_id` 定位轮次。赛况页兼容旧数据中同名、同性别、同类别、同组别的多个 event，并按轮次展示。
- 当前代码中的认证已是账号密码登录，401 清除登录状态并跳转登录页，并非旧说明中的微信静默重登。

本次数据流：

```text
管理端录入成绩 → 现有 ResultService / ResultMapper → result 表
                                                   ↓
小程序赛况 → /api/result/listByEvent → PublicResultVO（展示字段）
          → /api/sports-meeting/list（运动会）
          → /api/event/list（项目）
          → /api/schedule/list（轮次顺序）
```

## 问题与已落实的改进

| 原问题 | 本次改进 |
| --- | --- |
| 只有进行中赛事，结束后入口消失 | 增加“历史赛况”，查询已结束赛事；没有进行中赛事时给出历史入口 |
| 项目多时只能逐个翻找 | 名称/组别/性别关键词搜索，分类与组别组合筛选，可重置 |
| 每次返回会重置运动会、展开项 | 返回和下拉刷新保留仍有效的运动会、筛选条件、展开项目，重新获取数据 |
| 快速切换后旧请求覆盖新页面 | 运动会列表和当前选择分别使用请求版本号，忽略过期响应 |
| 多次点击会重复请求，加载状态全局共享 | 每个项目独立维护 idle/loading/ready/error，按需请求并去重 |
| 请求失败被吞掉，显示“暂无成绩” | 区分请求失败、尚无成绩、项目为空与筛选无匹配，并提供重试 |
| 合并 event 后的成绩顺序可能错误 | 每轮合并后重新排序；田赛降序，径赛/团队赛升序，未录入放末尾且不编号 |
| 轮次接口较慢导致顺序不稳定 | 项目和轮次并行获取，完成后再加载成绩；轮次失败时显示降级提示 |
| 长距离项目只显示总秒数 | 超过一分钟显示“分、秒、毫秒”，田赛显示两位小数米 |
| 小字号、低对比度与截断信息 | 蓝白卡片、分类标识、清晰表格；长姓名/学院换行，窄屏文字和点击区域设下限 |
| 小程序使用管理端成绩接口 | 新增只读 `/api/result/listByEvent`，仅返回展示字段，排除手机号、学号、专业、participantId 等 |

新接口只允许查看进行中/已结束运动会的有效项目。继续复用原成绩服务和 SQL 查询，没有执行数据库写操作，也没有修改表结构或管理端录入流程。

“序位”只是依照已有成绩排序的展示顺序，保持原有逐行编号规则，不新增并列名次、判罚或成绩发布规则。页面提示最终名次以赛事公告为准。团队赛也沿用现有按参赛人员存储、按时间排序的口径。

刷新采用进入/返回页面及手动下拉触发，不代表实时推送。已展开成绩随刷新重新获取，关闭的项目按需获取，避免首屏一次请求全部成绩。

## 验证

- `node --test tests/match.test.cjs`：12 项通过，覆盖分组、组合筛选、排序/单位、过期响应隔离、去重/重试、刷新保留条件、历史切换、降级状态、慢轮次请求及部分成绩请求失败。
- `mvn -o -DskipTests compile`：后端编译通过。
- `mvn -o -Dtest=UserResultControllerTest -DforkCount=0 test`：4 项 MockMvc 测试通过，覆盖 JSON 字段过滤、已结束赛事、空成绩、无效项目与不可查看赛事。这些测试使用服务替身，不连接数据库。
- 本机微信开发者工具的 `wcc.exe`、`wcsc.exe`：WXML/WXSS 编译通过。
- 使用原生 WXML 编译产物生成模拟数据预览，检查 320/375/430 像素宽度及 812 像素横屏：页面和姓名、成绩列未检测到横向溢出；已检查 320/375 像素截图。预览仅作布局验证，不包含真实赛事数据。
- 真实微信运行、真机字体缩放以及与实际数据库数据的联调仍需在开发者工具中验收；模拟数据样式预览不能替代真机验证。

## 后续建议（未纳入本次变更）

1. **统一文档和状态定义**：现行管理端、小程序使用 `0=筹备、1=报名、2=进行中、3=结束`，但 `sports_meeting.sql` 和数据库设计文档仍是旧三态注释。建议核对实际数据库后统一维护；涉及数据库写入时先确认。
2. **补齐管理端鉴权**：当前 `/api/admin/**` 未纳入拦截器。本次只缩减了赛况页使用的新接口的返回字段，原管理接口的访问控制仍需单独完善。
3. **明确官方名次与成绩发布**：若需要并列名次、取消资格、人工裁定或审核后公布，应由后端保存规则和发布状态，两端共享，不在小程序自行推断。
4. **随数据量扩展读取方式**：大量项目/成绩时增加后端分页、按项目组批量取成绩；若需要赛事直播，再评估定时刷新或推送。本次保留按展开项目加载的低开销方案。

## 本地查看

先重启后端以加载新接口，再在微信开发者工具重新编译 `sportdocu/`，打开底部“赛况”。检查运动会切换、历史入口、筛选、展开/收起、断网重试和下拉刷新。
